# Panel API 1.0.0 / major 1

## Точки входа

`PanelModule` загружается стандартным Java ServiceLoader. JAR должен содержать `META-INF/services/ru.bccontrol.panel.api.PanelModule` с полным именем провайдера. API находится в classloader хоста; включать классы `ru.bccontrol.panel.api` в JAR модуля запрещено. Хост проверяет apiMajor до create(). Сейчас поддерживается один провайдер панели в каталоге modules; при нескольких требуется убрать лишний. Отсутствие модуля и несовместимость показываются внутри вкладки, основной редактор продолжает работу.

`create(PanelHost)` возвращает `PanelView` с JavaFX Node и close(). Данные/компоненты принадлежат хосту; модуль получает immutable DTO и не должен хранить ссылки на внутреннюю модель хоста. Это граница зависимостей, а не песочница Java-кода: устанавливается доверенный модуль.

## Потоки и жизненный цикл

Вызовы UI/API snapshot, subscribe/watch и доставка Snapshot выполняются на JavaFX Application Thread. Первый Snapshot приходит при subscribe. Подписку нужно закрыть; при close представления также освобождаются watch-привязки. View не закрывает общий transport. Перевод сетевых операций в рабочий поток — задача хоста. CompletionStage команд не гарантирует UI-поток; возвращаться к UI нужно через Platform.runLater.

Snapshot содержит идентификатор сессии, connected, компоненты/поля, значения только наблюдаемых Ref и capabilities. Компоненты адресуются иерархическим путём без временных SOX ID. Ref = componentPath + field. watch полностью заменяет набор текущего представления (лимит хоста 64), не инициирует connect. Доставка значений зависит от опроса хоста. В Studio до 4 наблюдаемых компонентов добавляются за цикл по кругу в общий пакет до 16 блоков; другие приоритеты редактора сохраняются.

Sample: полное строковое value, Quality (GOOD/STALE/OFFLINE/LOCAL/ERROR), timestampMillis фактического чтения (0 для локального), detail. LOCAL может означать неприменённый черновик, а не состояние контроллера. Недоступная привязка отсутствует в values. Поля credentials/password/meta не передаются адаптером Studio.

## Команды

WRITE и ACTION доступны только при соответствующей capability и разрешённом поле. Результат CONFIRMED, REJECTED или UNKNOWN. При UNKNOWN повтор запрещён без новой проверки состояния. Ни загрузка модуля, ни открытие документа/представления не должны вызывать команды. В текущем production-адаптере Studio capability только READ и оба метода возвращают REJECTED. В DemoHost команды меняют только искусственное состояние.

## Документ

loadDocument/saveDocument работают с отдельным документом панели текущей сессии. Хост не разбирает widget schema, но ограничивает размер и сохраняет предыдущую копию. Виджеты/привязки и миграции принадлежат модулю. Не сохранять в документе пароли и transport-объекты. Неизвестная версия не должна автоматически перезаписываться.

## Совместимость

Не удалять/не менять сигнатуры существующих API методов, конструкторов DTO и enum-значений внутри major 1. Расширение record-компонентов также может нарушить ABI. Новые возможности добавлять совместимо с проверкой capabilities; несовместимые изменения требуют следующего major и обновления адаптера. Тестировать внутренний модуль сначала на DemoHost и API-контрактах в этом же проекте, затем на адаптере редактора. Код виджетов не должен импортировать Studio/Sedona/MCS/Baja или открывать SOX соединение самостоятельно.
