# Sedona Studio 0.1.0 — самостоятельный JavaFX-редактор

13 ноября 2026. Рабочая начальная версия отдельного настольного приложения. Windows x64 проверен с приложенным Java/JavaFX runtime. MCS, Niagara, Workbench, браузер и Node для работы не требуются. Старые редакторы, установленные модули MCS и устройства не изменялись.

## Запуск Windows

Открыть `releases/0.1.0/SedonaStudio/SedonaStudio.exe` или `dist/SedonaStudio/Start.cmd`. Папку SedonaStudio можно переносить целиком. Рядом находятся приложение, библиотека Sedona и обычный Java runtime со своими upstream-лицензиями. Первый запуск открывает локальную демонстрационную схему. Никакие устройства автоматически не подключаются.

## Что работает

- Нативное полотно JavaFX: блоки, все доступные поля, кривые соединений, перемещение по сетке, прокрутка, масштаб, папки и дерево.
- Палитра: девять реальных базовых типов офлайн; после подключения — конкретные доступные типы текущей схемы устройства, с точным kit/checksum. Блоки с учётными данными исключены из создания.
- Добавление, дублирование одного блока, переименование, изменение числовых/Boolean полей, создание/удаление связей, удаление блока с поддеревом в локальном документе. Undo/redo до 100 операций, Ctrl+Z/Y, Ctrl+D, Delete, Ctrl+S. Связи проверяют типы и один источник на вход.
- Имена компонентов учитывают ограничение Sedona в семь ASCII-символов. При изменении координат сохраняются младшие биты `meta`, включая группу доступа; при создании берётся исходная группа из default типа.
- Восемь тем: Arctic, Sage, Sand, Lagoon, Pearl, Copper, Blueprint, Original. Тема и размеры панелей сохраняются через пользовательские Java Preferences. Тренд и боковые области растягиваются разделителями.
- Файлы `.sedona.json`: формат v1, явная модель, ограничение 4 MiB, проверка структуры, атомарная замена и предыдущий `.bak`. Имена секретных полей отфильтрованы; пароль соединения в файлы не записывается.
- Одна явная SOX/DASP-сессия. Отдельный поток ввода-вывода, без операций сети на JavaFX-потоке, автопереподключения и автоматических повторов записи. Пароль вводится на подключении и остаётся в памяти.
- Манифесты: точные имена/checksum, локальный кэш, автоматический GET архива и XML при отсутствии файлов. Менеджер позволяет импорт XML/ZIP и экспорт точного набора проекта. Если устройство возвращает not found и не содержит нужного XML, клиент сообщает ошибку — восстановить определения из одного checksum невозможно.
- Выборочное чтение: по явному включению, раз в секунду, максимум восемь выбранных/наблюдаемых компонентов. Значения показаны как кэшированные UI-отсчёты. До восьми трендов, по 300 отсчётов; удаление сигналов через контекстное меню, CSV. При недопустимом отсчёте или разрыве более 2.5s буфер соответствующей кривой очищается, чтобы не соединять линией интервалы без данных. Это временное ограничение текущего native LineChart; долговременного архива нет. Большие long в графике преобразуются в double; точное значение доступно в инспекторе и JSON. Опрос выключен по умолчанию и при ошибке прекращается.
- Применение изменений к уже прочитанному устройству: подробный план и отдельное подтверждение, свежая схема/идентификация/значения перед записью, операции создания/переименования/параметров/координат/связей/удаления, чтение результата. Вход, остающийся связанным, вручную не перезаписывается.
- До первой записи: копия существующего сохранённого `app.sab`, `kits.scode`, точных манифестов и JSON-снимок текущей структуры/параметров. Исходный `app.sab` читается без предварительного App.save; несохранённое состояние RAM представлено отдельно JSON-снимком без секретных полей. Служебные двоичные копии остаются в локальном каталоге операций и не включаются в поставку.
- Перед каждым изменением синхронно записывается ATTEMPT, после успешного шага — DONE. Итог проверяет существование блоков, имена, поля и связи. При сбое сохраняется журнал частичного результата, последующие записи требуют повторного чтения устройства. Автоматического отката нет: SOX-операции не образуют транзакцию.
- App.save вызывается только по отдельной галочке в подтверждении после проверки изменений. Проверка сохранности после перезапуска контроллера в этот этап не входила.

## Работа с проектом

Для локальной схемы дважды щёлкнуть тип в палитре. Нажать выход справа, затем вход слева. Поля меняются кнопкой «Изменить» в инспекторе. Офлайн-схема не вычисляет алгоритмы блоков: реальные значения получаются от Sedona VM.

Чтобы изменить устройство, подключиться, дождаться чтения, отредактировать локальную копию и открыть «Применить». Сохранённый снимок с теми же точными китами можно открыть поверх подключённого устройства как черновик; перед применением всё равно выполняется свежая проверка. Пустой офлайн-проект пока не превращается автоматически в полноценную прошивку устройства.

Файлы приложения Windows: `%LOCALAPPDATA%/BCControl/SedonaStudio`, кэш — `cache`, журналы/копии операций — `operations`. При прямом запуске JAR используются те же пользовательские пути. В папках установленного MCS редактор ничего не сохраняет.

## Архитектура и рефакторинг

- `model`: Project/Node/Port/Wire, валидация, History, SecretFields. Никаких JavaFX, MCS или сетевых объектов.
- `storage`: формат JSON, атомарное сохранение, каталог, журнал намерений/результатов.
- `protocol`: DeviceSession, единственный SOX-адаптер, проверка скаляров, архивы манифестов. Используется обычный публичный `sedona.jar`.
- `ui`: JavaFX-приложение и отдельный DiagramPane с событиями через Host-интерфейс. Полотно не обращается к транспорту и не изменяет доменную модель напрямую.
- `sedona.sox.SchemaParts`: небольшой пакетный адаптер к штатному API запросов Sedona, необходимый для чтения списка китов до загрузки схемы.

Происхождение повторно использованных исходников и SHA256 библиотеки — provenance.json. Это отдельная ветвь выделения независимого ядра; код предыдущих MCS- и React-редакторов сохранён. Исторические генераторы лежат в tools/history, актуальные исходники — в src.

## Проверки

`python -X utf8 test.py` — проверки ядра. `python -X utf8 test.py --local-sox` — дополнительный интеграционный тест на собственной локальной native SVM, только 127.0.0.1:13987. Для него нужен Sedona SDK, путь задаётся SEDONA_TEST_SDK; исходная локальная конфигурация использует F:/Sedona/sedonadev-master. Прошивки и внешние контроллеры тест не меняет.

В тестах: пустой кэш → загрузка архива с VM → точная схема, создание и конфигурация блоков, группы доступа meta, связь, переименование, перемещение, запись с readback, отказ устаревшего значения до изменения, удаление, обязательные копии и журнал. JavaFX --smoke проверяет палитру, дублирование, удаление, историю и отрисовку; PNG содержит демонстрационные данные.

## Сборка и переносимость

Для сборки нужен OpenJDK 17. Зависимости OpenJFX 17.0.12 закреплены в lib/javafx/dependencies.json; `python -X utf8 link_runtime.py` получает публичные Windows JAR и создаёт минимальный runtime через jlink. `python -X utf8 build.py` собирает приложение с target --release 17. `python -X utf8 package_windows.py` создаёт папку с нативным EXE через jpackage, без установки MCS или системной Java. Исходники обычной библиотеки Sedona не менялись. Классы MCS/Baja/WireSheet в приложении и Sedona dependency запрещены проверкой сборки.

Исходный код использует переносимые Java/JavaFX API. Linux/macOS требуют соответствующего JavaFX runtime и своего запуска; при модульном JavaFX можно задать JAVAFX_LIB для start.sh. Готовые пакеты и фактические испытания Linux/macOS пока отсутствуют. Windows-runtime нельзя переносить как исполняемый runtime на другую ОС.

## Границы версии

Это начальная инженерная сборка, а не завершённая замена всех возможностей MCS. Пока отсутствуют компиляция/загрузка полного набора прошивки и новых китов, SAX/SAB-редактор офлайн, симулятор алгоритмов, многоосевые/архивные тренды, многопользовательская работа и автоматическое восстановление после частично применённых структурных изменений. Системные компоненты/User/Service не удаляются этим редактором; смена типа и родителя существующего блока, копирование поддерева и редактирование строк/Buf не поддерживаются. При неизвестном результате записи нужны чтение устройства и анализ журнала.

Проверки записи выполнены на локальной native SVM. На физических устройствах новая программа в этом этапе не испытывалась. Подпись/установка модулей MCS, остановка платформы и изменение <development-host> не выполнялись.

## Геометрия и связи 0.1.3

Раскладка SOX передаёт координаты в meta (x: старший байт, y: следующий, шаг 12), но не ширину/высоту карточки. Это сверено с Ontrol BSoxVirtualComponent / BMetaFE, которые передают p=x, q=y в BWsAnnotation. Комментарий исходного sys::Component в SDK имеет другой порядок осей; существующую совместимость с Ontrol/MCS сохраняем.

Редактор измеряет настоящие layoutBounds карточек после CSS и layout, без тени. Высота зависит от числа портов; ширина фиксирована 220 логических px, длинные подписи сокращаются с подсказкой. По умолчанию пересекающиеся карточки разводятся только в представлении, с сохранением исходных координат проекта и устройства. Настройки позволяют выключить это. «Закрепить раскладку» сохраняет экранные координаты текущей папки в проект одним действием undo; запись на устройство по-прежнему только через «Применить». Закрепление отклоняет позиции вне протокольного диапазона 0…3060. Полотно расширяется по габаритам блоков; «Вписать» использует реальные размеры.

Трассировка адаптирует подход MCS LinkSnakeGlyph: сетка занятости компонентов, свободные ортогональные участки и поиск обхода. Реализация самостоятельная JavaFX: A* с ценой поворотов/занятых проводами клеток, стрелки у входов, цвет bool-сигналов. При отсутствии свободного пути связь отображается концами, без ложной линии сквозь блок. Это не побитовый перенос исходного MCS класса и не гарантия отсутствия всех пересечений проводов. Модули MCS/Baja в приложение не добавляются.

Проверены перекрывающиеся блоки с 16 портами, сохранность исходного проекта, закрепление/undo, тесные реальные карточки, обход препятствия, обратная связь и петля к своему блоку. Исходные материалы исследования: build/mcs-routing (не нужны для запуска). Геометрические снимки — синтетическая локальная схема, не устройство.

## Полная палитра 0.1.5

Палитра строится по манифестам: дерево «точный кит name-checksum → типы компонентов», выбор кита, поиск по киту/типу, свойства с типами/config/readonly/default в подсказке. Добавление — кнопкой, двойным щелчком на типе или перетаскиванием. Ветки китов сами не добавляются на схему. Дерево проекта осталось отдельной вкладкой.

При подключении используется только каталог точной схемы устройства. Офлайн читается собственный локальный cache/manifests; в чистую установку включены 22 набора публичных SDK-манифестов (135 доступных типов). На машине с дополнительными манифестами типов будет больше. «Локальные манифесты» обновляет каталог, а «Манифесты» импортирует XML/ZIP. После офлайн-импорта каталог обновляется. Контрольная сумма видна для каждой версии; отметка «локальный» означает, что кит пока отсутствует в проекте, а не наличие его на контроллере.

Абстрактные, testonly, palette=false, служебные типы sys (кроме Folder), наследники Service и типы с чувствительной конфигурацией скрыты. Свойства наследуются из разрешённой Schema. При добавлении офлайн включается замыкание зависимостей; смешивание разных checksum одного кита в проекте отклоняется. Неразрешённые зависимости выводятся в журнал; сетевое скачивание при чтении локального каталога не выполняется. Палитра не устанавливает бинарные киты на контроллер.

Проверки: чистый cache → 135 типов/22 набора/0 ошибок; поиск Ramp и выбор листа дерева; 33 проверки ядра; локальный native SVM на 127.0.0.1:13987 (каталог, создание/config/link/readback). ## Сессии и пароли 0.1.6

«Сессии» создаёт именованный профиль и открывает его отдельным окном/JVM. Сохраняются адрес, порт, пользователь, черновик проекта и активный список точных манифестов. Каждая сессия использует sessions/<id>/cache/manifests, draft.sedona.json (+ предыдущий .bak), manifest-set.json и operations. Глобальные статические кэши Sedona изолированы процессами. Повторное открытие одной сессии блокируется файловым lock; другие сессии могут работать одновременно. При запуске соединение не устанавливается. Черновик автоматически восстанавливается. Старый общий cache остаётся на месте, автоматически во все сессии не копируется.

«Локальная библиотека» — отдельная рабочая сессия с SDK-каталогом. При подключении из неё создаётся профиль устройства в новом окне: в нём нужно нажать «Подключиться». Смена адреса/порта уже настроенного профиля также создаёт другую сессию. В сессии устройства офлайн-палитра ограничена последним прочитанным manifest-set.json; ранее закэшированные версии от другой прошивки не смешиваются в активной палитре.

При подключении отсутствующие точные манифесты запрашиваются непосредственно у контроллера (m:m.zip, m/m.zip, затем m:<name-checksum>.xml). В кэш сохраняются только требуемые китовые версии, а не весь полученный архив. Веб-подстановка через ManifestDb при отсутствии локального файла обходится. Если контроллер не содержит архив/XML, драйвер сообщает это явно: восстановить отсутствующий манифест из одного checksum невозможно.

Флажок «Сохранить пароль» использует Windows DPAPI CurrentUser с энтропией ID сессии. В profile.json хранится только passwordDpapi, секрет не попадает в проект/аргументы процессов/журналы. Подстановка сохранённого пароля выполняется в маскированное поле. Снятый флажок убирает сохранённый пароль при следующей попытке подключения. На другой Windows-учётной записи/компьютере пароль потребуется ввести заново. В других ОС plaintext fallback отсутствует; хранение DPAPI не поддерживается.

Проверки: два независимых каталога с одинаковыми kit names каждый отдельно скачивает нужные манифесты; лишние версии архива не импортируются; последующая загрузка офлайн без fetch; DPAPI roundtrip и запрет дешифрования blob с ID другой сессии; отсутствие plaintext в файле; локальный native SVM, физические устройства не менялись.

## Версия 0.2.0 — первые два этапа

Запуск текущей версии: `Start-SedonaStudio.cmd` в корне проекта. Он читает номер из `SEDONA_STUDIO_CURRENT.json` и запускает соответствующий EXE в releases. Python/JDK для запуска не нужны; runtime входит в сборку. Старые версии остаются на месте. Настройки и профили сохраняются отдельно от каталога версии. Схема JSON обратно совместима: комментарии и маршруты — необязательные поля.

Стабилизация:

- Свежие значения отмечаются зелёным; устаревшие и офлайн — приглушённым цветом; локальные изменения — оранжевым. Подсказка над значением поясняет состояние и возраст ответа. Порог устаревания: больше трёх интервалов опроса, минимум 3 секунды. На паузе данные считаются устаревшими. Цвет не означает исправность технологического оборудования.
- Опрос не меняет черновик и историю отмены, не пересчитывает трассы и не блокирует редактирование. Опрашиваются видимые блоки, выбранный и тренды; в скрытой вкладке — только тренды. Большие виды опрашиваются порциями, поэтому возраст конкретного блока может отличаться.
- Черновик сессии сохраняется атомарно, предыдущий файл остаётся .bak. Если при запуске основной черновик повреждён, используется исправный .bak; повреждённый оригинал сохраняется рядом как .damaged-UUID. При недоступности обеих копий выводится ошибка.
- Apply сохраняет структуру, app.sab, kits.scode, архив манифестов и журнал намерений перед записью; проверяет результат чтением обратно. Автоматического повтора при неопределённом результате нет.

Редактирование:

- Рамка на свободном месте выделяет группу. Ctrl/Shift добавляют или исключают блок. Ctrl+A выделяет текущую папку. Перемещение группы сохраняет взаимное расположение и отменяется одним Ctrl+Z. Стрелки перемещают группу; Shift+стрелка — точнее.
- Ctrl+C / Ctrl+V / Ctrl+D копируют выбранные поддеревья вместе с внутренними связями. Внешние связи при копировании не добавляются. Буфер действует в текущей сессии и позволяет вставлять в другие папки.
- Меню «Редактирование»: выравнивание слева/сверху, распределение по габаритам карточек с зазором, перенос в папку, подсветка предшествующих и последующих блоков сигнала.
- Перенос в папку сохраняет внешние связи. При Apply компоненты создаются на новом месте, связи переносятся, прежние удаляются; это не атомарная операция контроллера. Группы доступа из meta сохраняются. Перед Apply показывается план.
- В инспекторе можно сохранить комментарий к блоку или папке. Комментарии, именование папок и ручные маршруты хранятся в локальном проекте, протокол Sedona их не передаёт. Для передачи другому ПК нужен файл проекта.
- Двойной щелчок по связи добавляет ручную опорную точку. У выбранной связи видны оранжевые маркеры; их можно двигать. Контекстное меню возвращает автотрассировку. Ручной маршрут подчиняется точкам пользователя и может проходить через блоки. При общем перемещении концов/копировании группы точки смещаются вместе с ней.

Вкладки сессий:

- Сверху показаны открытые сессии. Нажатие переключает в уже запущенную сессию; её соединение, тренды и история остаются в памяти. Без галки «Открыть в новом окне» исходное окно скрывается после подтверждения готовности выбранного; с галкой оба видны.
- У каждой сессии отдельный процесс, кэш манифестов, черновик, пароль DPAPI и транспорт. Это необходимо из-за статических кэшей Sedona Java. Расход памяти растёт с числом открытых сессий; вкладки не являются одним общим Java-процессом.
- При закрытии видимого окна скрытые фоновые сессии сохраняют черновики и завершаются; отдельно видимые окна продолжают работу. Обычное открытие профиля не подключает устройство. Подтверждённый Connect передаёт пароль один раз в зашифрованном виде.

Проверки 0.2.0: core 33; команды групп/поддеревьев и undo/redo; восстановление повреждённого черновика; две изолированные схемы манифестов; DPAPI; локальный native SVM 127.0.0.1:13987 с созданием/переносом/внешними связями и проверкой групп доступа; живой Ramp и состояния свежести; нативные JavaFX события выделения/переноса/линков/масштаба; переключение двух сессий с возвратом в исходный PID и завершением скрытого процесса.

Итоговая автотрассировка после отпускания всё ещё может занимать время на сложных схемах. Проверок с тысячами блоков и длительного ресурсного прогона на слабом ПК пока нет.

Координаты портов вычисляются последовательными преобразованиями внутри полотна, без обхода через экранные координаты и обратное масштабирование. Это исключает дополнительное округление из экранного преобразования при вычислении концов связи.

Проверки: нативные JavaFX события выбора связи, повторное использование маршрутов при изменении комментария/значения, сброс кэша при перемещении, IO на дробных координатах, масштабирование и перетаскивание; core, манифесты, пароли/профили, mailbox, переключение двух сессий и закрытие фоновой вкладки. Плотные схемы после изменения геометрии всё ещё требуют полного поиска маршрутов; ограничение на больших схемах остаётся.

## Версия 0.2.3 — быстрые свободные коридоры

Для связи слева направо редактор сначала проверяет несколько простых ортогональных коридоров. Свободный коридор строится без A*. Проверка учитывает препятствия на той же сетке с защитным зазором; занятые участки не используются быстрым путём. Обратные/самосвязи, препятствия и занятые коридоры остаются на прежнем ограниченном поиске A* с учётом других проводов. Это снижает работу при изменении геометрии простых схем, сохраняя существующий алгоритм для сложных обходов.

В стендовом сравнении с 0.2.2 на этой машине: 100 независимых связей между 200 карточками, 2 разогрева и 7 измерений — медиана расчёта маршрутов 6,81 мс → 2,32 мс. Измерение исключает создание JavaFX элементов, перерисовку, мышь и схемы с препятствиями; оно не означает такое же ускорение всей программы или слабого компьютера. Отчёт: build/route-benchmark/comparison.json.

Добавлен воспроизводимый тест WireRouterTests: 100 свободных связей без A*, точные дробные центры портов и горизонтальные выходы, ортогональность, обход карточек, самосвязь, занятые коридоры, непроходимая стена. Дополнительно 200 сцен с препятствиями и фиксированным начальным числом генератора: все 200 построенных путей проверены на пересечение карточек; 116 использовали быстрый путь и 84 — A*. Код работы с устройством не изменялся.

## Версия 0.2.4 — диагностика связей и рабочее пространство

При наведении на связь показываются источник и получатель: имя блока/слота, ID, тип компонента и слота, значение и состояние свежести. По щелчку эти данные доступны в правом инспекторе. Значения отображаются раздельно: SOX читает компоненты последовательно, поэтому они могут относиться к разным моментам; несовпадение само по себе не считается ошибкой связи. Строковые значения в диагностике ограничены 512 символами. Инспектор и открытая подсказка обновляются без изменения проекта и трассировки. Для выбранной связи оба конца получают приоритет в существующем ограниченном опросе.

Кнопки «К источнику» / «К получателю» открывают нужную папку, выделяют блок и прокручивают к нему холст. Те же переходы есть в контекстном меню связи. Навигация не меняет граф и не отправляет команды устройству.

В папке каждой сессии сохраняется отдельный workspace.json: текущая папка, масштаб, горизонтальная/вертикальная прокрутка, положения разделителей палитры/инспектора/нижней панели и выбранные вкладки боковой/нижней панели. Запись выполняется после паузы в изменениях и перед переключением или закрытием сессии, атомарно через временный файл. Состояние вида отделено от черновика схемы и паролей.

Папка восстанавливается с проверкой проекта (имя, платформа, точные киты) и цепочки имён/типов папок. Если проект изменился или папка исчезла/ID переиспользован, старая папка не открывается. При первом подключении схема вписывается; при повторном чтении того же проекта сохранённый вид сохраняется. Открытие сессии по-прежнему не подключает устройство автоматически.

Проверено: сохранение/восстановление вида между двумя отдельными JavaFX процессами без соединения; изоляция сессий, ограничения чисел и повреждённый JSON; настоящие кнопки перехода к концам связи с неизменным графом; полное значение и офлайн-статус в диагностике. На отдельном native SVM 127.0.0.1:13987 проверена реальная связь func::Ramp.out → math::Add2.in1: оба конца опрашиваются, значения и статус обновляются в инспекторе, без перетрассировки и изменения черновика. Физические устройства не затрагивались.

Дополнительные проверки: `python -X utf8 tests/view_restart_smoke.py`, `python -X utf8 test.py --live-ui`. Общие ограничения производительности предыдущих версий сохраняются.

## Версия 0.2.5 — устойчивое обновление значений

Исправлено отключение опроса общей обработкой ошибок редактора. Ошибка локального редактирования/открытия диалога теперь не выключает живые значения. Операции чтения/применения по-прежнему явно управляют своей паузой; автоматического подключения или повтора записи нет.

Чтение выполняется по блокам с сохранением частичных успехов: сбой одного компонента не отбрасывает ответы остальных. Для неудачного блока вводится пауза 10 секунд перед следующим чтением; другие блоки продолжают опрашиваться. При потере связи дальнейшие запросы прекращаются, переподключение остаётся ручным. Возраст значений считается от фактического времени чтения каждого блока. Отдельно видны ошибка чтения, ожидание повторного чтения, отсутствие видимых блоков и длительное выполняющееся чтение.

Исправлено отображение read-only выходов: отличие старого снимка от baseline не считается локальным изменением read-only слота и больше не скрывает живое значение. Изменённые пользователем доступные для записи поля по-прежнему показывают проектное значение со статусом «ещё не применено».

Нажатие на индикатор обновления над холстом открывает меню «Обновить сейчас / возобновить», «Приостановить» и настройки. Основные параметры остаются в настройках. Команда возобновления требует существующего соединения; сама подключение не создаёт.

В папке сессии записывается studio.log; после 1 MiB он заменяет studio.previous.log. В журнал не записываются профили/пароли или дампы значений. Ошибка записи журнала не влияет на UI/опрос. Папка доступна через «Сессии → Открыть папку».

Проверено: частичный отказ блока с сохранением успешных ответов, остановка чтений при потере соединения, пустой результат при полном отказе и ротация журнала. На локальном native SVM 127.0.0.1:13987 проверена искусственно вызванная ошибка редактора с настоящим диалогом: опрос остаётся включён, значения Ramp продолжают меняться в диагностике, граф и маршруты не меняются. Реальный случай пользователя не был воспроизведён в работающем редакторе: во время проверки его процессы были закрыты и предыдущая версия не сохраняла журнал.

## Версия 0.2.6 — интервал обновления в миллисекундах

«Настройки → Интервал обновления, мс» теперь содержит числовое поле 100–60000 мс вместо списка секунд. Допустимы, например, 100, 200, 250, 500, 1000 или 2000 мс. Значение сохраняется в liveIntervalMs; при отсутствии нового значения прежнее liveInterval (секунды) пересчитывается в миллисекунды. Некорректное значение не позволяет нажать OK, отмена сохраняет прежние настройки.

Системный запуск раз в секунду заменён планированием следующего чтения по заданному интервалу. Устаревшие запланированные вызовы отменяются, одновременно выполняется только один последовательный пакет чтения. Если связь медленнее выбранного интервала, запросы не накапливаются. Изменение интервала и команда возобновления будят планировщик сразу. Проверки вкладок и обновление состояния кэшированных подписей выполняются отдельно примерно раз в секунду; успешные ответы выводятся сразу.

Порог устаревания учитывает миллисекундный интервал (не меньше 1 секунды, либо три интервала). Возраст свежих данных меньше секунды отображается в мс. Фактическая частота зависит от скорости устройства, связи и количества опрашиваемых блоков; интервал относится к пакету чтения, а не гарантирует одинаковый период каждого блока большой схемы.

Проверено: границы поля, ввод 250 мс и отмена в настоящем JavaFX диалоге; перенос прежних секунд и защита от некорректных/переполненных значений; local native SVM 127.0.0.1:13987 — при настройке 200 мс получено 25 успешных пакетов за 5 секунд, с последовательным executor, обновлением живой связи и неизменным графом/маршрутами. Физические устройства не затрагивались.
